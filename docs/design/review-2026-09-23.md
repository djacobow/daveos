# DaveOS design review — 2026-09-23

Reviewed at `cca30ac` on 2026-09-23, using the two earlier reviews
([Claude](design_review_claude.md), [Astra](design_review_astra.md)) and the
[fundamentals decision record](fundamentals.md) as the touchstone.

This is a structural review: repository layout, library boundaries, build and
feature selection, test and qualification coverage, documentation, and the
network-facing surface. No builds or hardware runs were performed for it;
hardware statements come from the commit bodies, `TODO.md` and
[the H563/H755 record](../hil-review-2026-09-22.md).

## Findings

### 1. The unauthenticated network surface now writes to the filesystem

Three services listen: console 1000, OTA 1001, file transfer 1002. The file
service accepts uploads, `rm`, `mkdir` and `rmdir` from any client on the LAN
when the volume is mounted `rw`. `docs/file-transfer.md` states the position
plainly ("This lab service has no authentication or encryption"), but the
exposure differs in kind from a console: the earlier risk was running commands,
this one writes and deletes files and stages firmware.

OTA requires an explicit `ota enable`; the file service has no equivalent gate.
Giving uploads and removals the same explicit enable, so the default listening
state is read-only, is a small change while the service is new.

### 2. CI never builds the two newest features

`file-transfer` and `ssd1306` appear nowhere in `.github/workflows/build.yml`.
`lib/net/file_transfer.hpp` is included only through the example's feature
table, so no CI job compiles it; only the portable half
(`lib/storage/transfer.cpp`) is covered, through host tests. An explicit feature
list means each new feature needs a line in the CI matrix — make that part of
the feature checklist before the next one lands.

### 3. Starter wrap pins are far behind

All three starters pin `88f03b5`, which predates the `features` option,
instance names, chrono-only scheduling and the library moves, so a starter
followed as published cannot configure its subproject. This is blocked on
publishing: `main` is 24 commits ahead of `origin/main`. It is the most visible
breakage for a new user.

### 4. The console example keeps absorbing features

`examples/stm32_console` is 22 files again (I2C, ADC, display, debug display,
SD, OTP, OTA, boot, health wiring). That is the intended shape now that reusable
parts live in `lib/`, and each feature adds only a thin adapter plus a table
entry. It remains the only place the full composition is exercised, and where
board wiring, demo commands and composition still mix. Watch that the next
feature's adapter stays thin.

### 5. One I2C bus, one boolean lease, two clients

The ADC and display share `I2cBus` through a single `leased_` flag in the
example. It works for two cooperating clients, but it does not generalize: no
queueing or fairness, and a client that forgets `release()` silently blocks the
other. The HAL already models multiple devices per controller. If a third client
appears, promote the lease into the HAL/registry layer instead of adding another
flag.

### 6. Deferred qualification is the main risk

Twenty open TODO items, mostly hardware qualification: physical power cuts
(deferred repeatedly), flash ECC injection, D-cache-enabled SPI DMA, card
removal, I2C clock stretching and repeated START, USB backpressure, H755 OTP.
The bootloader, OTA, SD writes and OTP all list power loss as unqualified, which
is the failure mode that corrupts a device in the field. Code is growing faster
than this backlog shrinks.

### 7. Still open from the earlier reviews

- **No board-support contract.** Adding a third board still means deriving the
  required interfaces from two `platform/stm32h*/` trees.
- **No machine-readable command manifest.** The typed argument metadata still
  only feeds `help`, though it already holds what a host tool would need.
- **`TODO.md`** now has four headings but still mixes 127 completed entries with
  20 open ones; there is no separate roadmap.
- **Documentation is ~8,200 lines** across 21 files, led by `reference.md`
  (1,271) and `PROJECT.md` (1,078). The split helped; the total still grows with
  the code.

## Suggested order

| Priority | Work | Done when |
| --- | --- | --- |
| 1 | Publish `main`, then move the three starter wrap pins | A published starter configures and builds against the pinned commit |
| 2 | Add `file-transfer` and `ssd1306` to the CI feature matrix | Every feature is built by CI on at least one board |
| 3 | Decide the file service's default posture | Writes require an explicit enable, or the choice is recorded as deliberate |
| 4 | Qualify one power-loss case, starting with the journal and A/B metadata | Interrupted power during commit leaves a bootable image, evidenced in a record |
| 5 | Write the board-support contract while the restructure is fresh | A checklist names every interface a new board must supply |

## Not recommended

- Restructuring directories again; the current layout matches both reviews.
- A generic driver framework or lifecycle protocol; the drivers added since the
  reviews fit the existing conventions.
- Consolidating documentation for its own sake. Prefer retiring superseded text
  when a subsystem changes.
